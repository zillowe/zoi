This document defines the official packaging standards for **Zoidberg**, the primary Zoi package registry. To ensure consistency, security, and quality, these guidelines adopt a rigorous policy-driven approach.

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**, and **OPTIONAL** in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

## 1. Applicability & Licensing

Zoidberg is dedicated to providing high-quality free and open-source software.

### 1.1. Tier Scope

- **`core` and `main` tiers**: These tiers **MUST** follow all guidelines in this document without exception. Software in these tiers **MUST** be Free Software (FOSS).
- **`extra` tier**: Guidelines in this tier are relaxed. It is intended for niche, specialized, or less stable packages where strict adherence to all FHS or bundling policies is not always practical. The source and verification rules in [section 5](#5-upstream-sources) still apply.

### 1.2. Free Software Requirement

All software in the `core` and `main` tiers **MUST** be under licenses determined to be Free Software by the [Free Software Foundation (FSF)](https://www.gnu.org/philosophy/free-sw.en.html) or the [Open Source Initiative (OSI)](https://opensource.org/osd).

### 1.3. SPDX Identifiers

The `license` field in `metadata()` **MUST** be populated with a valid [SPDX license identifier](https://spdx.org/licenses/) or expression.

- **Complex Licenses:** Use `AND`, `OR`, and `WITH` operators to accurately reflect multi-licensed software (e.g. `MIT AND Apache-2.0`).
- **Missing License Text:** If upstream fails to include a license file, the maintainer **SHOULD** contact upstream. If required by the license, a believed-correct copy of the license text **MUST** be included in the package via `zlicense()`.

## 2. Versioning & Revisions

Zoi uses an automated SAT solver that depends on strict, sortable versioning.

### 2.1. Upstream Versions (`version`)

The `version` field **MUST** match the upstream release version verbatim.

- **No Prefixes:** Do not include `v` prefixes (e.g. use `1.2.3`, not `v1.2.3`).
- **Leading Zeroes:** Do not trim leading zeroes if they are part of the upstream scheme.
- **Releases Only:** The version **MUST** name a release that upstream has published. Fixes taken from upstream after that release are carried as patches (see [5.5](#55-patches)) and do not change the version.

### 2.2. Downstream Revisions (`revision`)

The `revision` field tracks changes to the Zoi package definition itself.

- **Increments:** Increment the `revision` when fixing bugs in the Lua script, adding or removing patches, or updating dependencies while upstream remains the same.
- **Resets:** The `revision` **MUST** be reset to `"1"` whenever the upstream `version` is updated.

### 2.3. Snapshot Versioning

Snapshots are only permitted for software whose upstream has **never** published a release. They are not permitted in the `core` tier. A snapshot **MUST** use this format:
`[LAST_VERSION]^[YYYYMMDD]g[COMMIT_HASH]`

- **Example:** `1.0.0^20240320gabc123` (use `0^20240320gabc123` when there is no earlier release).
- **Rationale:** This ensures that snapshots sort higher than the last release but lower than the next release.
- **Source:** The source is the archive of that exact commit generated by the hosting service, pinned by hash like any other source (see [5.2](#52-source-precedence)).

## 3. "What Can Be Packaged" Policy

### 3.1. Bundling & Duplication

Packages **MUST** make every effort to avoid bundling (vendoring) libraries that are already available in Zoi or as native system packages.

- **Requirement:** If upstream supports building against system libraries, the package **MUST** be configured to do so.
- **Deletion:** Bundled third-party source code **SHOULD** be removed in `prepare()` to ensure the build process uses system-provided dependencies.

### 3.2. Pre-built Binaries in Source Builds

For packages providing a `source` build type, all binaries and libraries **MUST** be built from the source code included in the build process.

- **Prohibition:** Maintainers **MUST NOT** include pre-compiled `.o`, `.so`, or `.exe` files in a source build.
- **Exception:** This rule does not apply to content files (e.g. `.png`, `.pdf`) or "bootstrap" binaries required to build a compiler, provided those binaries are themselves open-source and temporary.

### 3.3. Impermissible Content

Zoidberg **SHALL NOT** host content that is:

- Legally questionable (patent-encumbered formats in certain jurisdictions).
- Offensive, discriminatory, or derogatory.
- Proprietary binary blobs (excluding permissible firmware for `core` hardware support).

## 4. Sub-package Separation Standards

To minimize the installation footprint and save bandwidth, large packages **MUST** be split into functional components using the following naming convention:

| Suffix  | Purpose                                                                                 |
| :------ | :-------------------------------------------------------------------------------------- |
| `:main` | **Primary Binary:** The main executable or CLI tool (if the package is split).          |
| `:lib`  | **Runtime Libraries:** Shared objects (`.so`, `.dylib`) and versioned runtime files.    |
| `:dev`  | **Development Files:** Headers (`.h`), static libraries (`.a`), and `pkg-config` files. |
| `:docs` | **Documentation:** Large manuals, HTML documentation, and examples.                     |

- **Dependency Chain:** The `:dev` sub-package **MUST** depend on the base package (or `:lib`) with an exact version match.
- **Default Install:** The base package (or `main_subs`) **SHOULD** only include the files necessary for standard execution.

## 5. Upstream Sources

Every package built from source starts from one archive of the upstream release, downloaded once and verified against a hash pinned in the recipe. This makes every build reproducible from the same bytes, independent of the state of upstream's version control, and fails loudly if those bytes ever change.

### 5.1. Archives, Not Repositories

Source packages **MUST** download a release archive in `prepare()`.

- **No Cloning:** Recipes **MUST NOT** fetch sources with `git clone`, submodule updates, or any other version-control checkout. Tags can be moved, histories rewritten, and version-control servers are far less reliable than release downloads.
- **One Release:** The archive **MUST** be the one for the exact `version` in `metadata()`. The URL **SHOULD** be built from the `version` variable so that a version update only changes the version and the hash.

### 5.2. Source Precedence

Maintainers **MUST** use the first of the following that upstream provides:

1. **The official release tarball.** The archive the project itself publishes for the release: its download page or release server, the GNU or kernel.org mirrors, release assets attached to a GitHub, GitLab, or Codeberg release, a PyPI sdist, or a crates.io crate. These are what upstream tests and signs, and often include generated files (such as `configure`) that a repository checkout lacks.
2. **The host-generated archive of the release tag.** Only when upstream publishes no tarball of its own, use the archive the source hosting service generates for the release tag:

   | Host            | Archive URL                                                         |
   | :-------------- | :------------------------------------------------------------------ |
   | GitHub          | `https://github.com/<owner>/<repo>/archive/refs/tags/<tag>.tar.gz`  |
   | GitLab          | `https://gitlab.com/<group>/<repo>/-/archive/<tag>/<repo>-<tag>.tar.gz` |
   | Codeberg/Forgejo | `https://codeberg.org/<owner>/<repo>/archive/<tag>.tar.gz`          |

- **Format:** When upstream publishes several compressions of the same release, prefer the one upstream signs, then the smallest (`.tar.xz` over `.tar.gz`).
- **Mirrors:** A recipe **MAY** try several URLs in turn (for example `ftpmirror.gnu.org` and `mirrors.kernel.org` for GNU software). Every URL **MUST** serve the identical file, verified by the same hash.

### 5.3. Mandatory Hashes

Every file downloaded in `prepare()` **MUST** be verified before it is extracted or used.

- **Algorithm:** `sha512` is **REQUIRED** for all new and updated packages. `sha256` is only accepted in existing recipes until their next version update.
- **Pinned in the Recipe:** The hash **MUST** be written in the recipe itself. It **MUST NOT** be fetched from the same server as the archive at build time.
- **Method:** Use `UTILS.DOWNLOAD(url, filename, "sha512-<hex>")`, `verifyHash()`, or `sha512sum -c` inside a shell step that runs with `set -e`. A failed check **MUST** stop the build.
- **Updates:** When the `version` changes, the maintainer downloads the new archive, checks its signature where available, and records its new hash. A hash mismatch on an unchanged version **MUST** be investigated before the hash is replaced.

```lua
local version = ZOI.VERSION or "2.8.1"

function prepare()
	sh([[
		curl -sSfL --retry 3 \
			"https://ftpmirror.gnu.org/gnu/patch/patch-$VER.tar.xz" \
			-o "patch-$VER.tar.xz"
		echo "<sha512 hex>  patch-$VER.tar.xz" | sha512sum -c -
		tar -xf "patch-$VER.tar.xz"
	]])
end
```

### 5.4. Chain of Trust (GPG)

For packages in the `core` tier, maintainers **MUST** verify OpenPGP signatures of upstream sources whenever upstream publishes them. Signature verification complements the hash: the hash pins the exact file, and the signature shows that upstream released it.

- **Committed Keys:** The upstream signing key **MUST** be committed to the package directory as `keys/pgp/<FINGERPRINT>.asc` (the full fingerprint, uppercase, no spaces). It is reviewed once when added, never downloaded at build time, and travels with the source bundle.
- **Key Source:** The committed key **MUST** be obtained from upstream's own published location (project website, release announcement, or keyring) and its fingerprint checked against one published by upstream.
- **Method:** Download the detached signature next to the archive and pass the committed key file to `verifySignature()`. It verifies against that key alone and does not modify any keyring. `verifySignature()` returns `false` on a bad signature, so the recipe **MUST** raise an error in that case.
- **No Keyring Changes:** Recipes **MUST NOT** call `addPgpKey()` to verify sources. It imports the key into the Zoi keyring of whoever builds the package, which is a side effect a build must not have.

```lua
function prepare()
	local tarball = "patch-" .. version .. ".tar.xz"
	sh([[
		curl -sSfL --retry 3 \
			"https://ftpmirror.gnu.org/gnu/patch/patch-$VER.tar.xz" \
			-o "patch-$VER.tar.xz"
		curl -sSfL --retry 3 \
			"https://ftpmirror.gnu.org/gnu/patch/patch-$VER.tar.xz.sig" \
			-o "patch-$VER.tar.xz.sig"
		echo "<sha512 hex>  patch-$VER.tar.xz" | sha512sum -c -
	]])
	local key = LOCATION.PKGLUADIR .. "/keys/pgp/<FINGERPRINT>.asc"
	if not verifySignature(tarball, tarball .. ".sig", key) then
		error("bad upstream signature on " .. tarball)
	end
	sh([[tar -xf "patch-$VER.tar.xz"]])
end
```

### 5.5. Patches

Changes to the upstream source are made with patch files, never by downloading a different upstream state.

- **Location:** Patches **MUST** be stored in the package directory next to the recipe and applied in `prepare()` after verification.
- **Naming:** Patches **SHOULD** be named `NNNN-short-description.patch` (e.g. `0001-fix-build-with-gcc-16.patch`) and applied in that order.
- **Provenance:** Each patch **SHOULD** begin with a header naming its origin (upstream commit, bug report, or mailing-list post), or stating that it is specific to Zoidberg.
- **Backports:** Fixes from an upstream release branch that are not yet in a release are carried this way on top of the latest release tarball. The `version` stays that of the release, and the `revision` is bumped when patches change.
- **Failures:** A patch that does not apply **MUST** fail the build. Do not apply patches with `|| true`.

### 5.6. Preparing the Source

- **Generated Files:** When the release tarball already ships `configure` and other generated build files, recipes **SHOULD NOT** regenerate them. Run `autoreconf` or `./bootstrap` only when a patch changes the build system or upstream requires it.
- **Fail Fast:** Shell steps in `prepare()` **MUST** run with `set -e` (as the `sh()` helper used throughout Zoidberg does), so a failed download, hash check, extraction, or patch stops the build instead of producing a partial source tree.

## 6. Staging & Integration

### 6.1. Manual Pages

Maintainers **MUST** use the `zman()` helper function to bundle manual pages. This ensures they are available via `zoi man` and placed in standard FHS-compliant locations.

### 6.2. License Staging

Every package (and every independent sub-package) **MUST** stage its license text to the package store using the `zlicense()` helper.

```lua
function package(args)
  -- Stage binary to main package
  if args.sub == "" then
    zcp("bin/tool", "${pkgstore}/bin/tool")
    zman("doc/tool.1")
  end
  -- Stage license (mandatory for all)
  zlicense("LICENSE")
end
```
